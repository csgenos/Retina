## Method, and its limits

This audit was produced in a Linux container with no GPU, no Windows host, and no
Computer Use tooling, so PowerShell and a live Minecraft launch were not possible.
Everything below was verified headlessly instead:

- `retina-core` was compiled and its **74 tests run green**. A JDK 25 is not reachable from
  this environment (`api.adoptium.net` is blocked by the egress proxy), so the toolchain was
  overridden to Java 21 with `-Pjava.version=21`. The module compiles and passes unchanged at
  that level, which is itself worth knowing.
- Every translator claim was checked by pushing real shader-pack GLSL through the project's own
  `SpirvCompiler` and reading the resulting SPIR-V — the same method
  `TranslationCompilesTest` uses. Quoted diagnostics are verbatim shaderc output.
- The std140 finding was checked by diffing `TerrainUniformLayout`'s arithmetic against the
  `OpMemberDecorate … Offset` decorations in a compiled module.
- `retina-fabric` **cannot be compiled here** — `maven.fabricmc.net`, `libraries.minecraft.net`
  and `piston-meta.mojang.com` are unreachable. Findings in that module come from source
  inspection and are marked as such. (Those hosts *are* reachable from GitHub's runners: once
  the wrapper's mode was fixed, CI compiled the module against real Minecraft 26.2, Loom and
  Sodium, ran the Fabric tests, and produced a verified release jar. So the fixes in that module
  are compile-verified — just not from inside the audit environment.)

The figures above describe the tree as audited, at `2d108ae`. The throwaway probes used to
reproduce each finding were replaced by permanent tests when the fixes landed:
`Std140LayoutTest` and `PackCompatibilityRegressionTest`, which take the suite from 74 to 88.

## Critical

### B1 — 42 of 60 uniform-block members are written to the wrong byte offset

`retina-fabric/src/main/java/dev/retina/render/TerrainUniformLayout.java:69`

`typeLayout` gives `vec3` a size of 16 bytes. Under std140 a `vec3` aligns to 16 but *occupies
12* — the next member packs into the gap. From the first `vec3` onward every offset Retina
computes runs 4–8 bytes ahead of where the compiler actually placed the member.
`ShaderRuntime.TerrainFrameUniform.write` uses those offsets directly, and
`TerrainShaderAdapter` emits the block in the same order, so CPU and GPU disagree about the
whole tail of the block.

Each affected uniform therefore reads the **previous** member's bytes. `fogEnd` receives
`fogStart`'s value; `near` receives `aspectRatio`; `sunAngle` receives `moonPhase`'s integer bit
pattern reinterpreted as a float. Matrices are unaffected because they sit at the head of the
block — which is why terrain still lands correctly and this has stayed invisible.

```
member                 type    retina   spirv   delta
cameraPosition         vec3       640     640       0
previousCameraPosition vec3       656     656       0
eyeAltitude            float      672     668      +4
frameCounter           int        676     672      +4
frameTimeCounter       float      684     680      +4
sunAngle               float      700     696      +4
…
eyeBrightness          ivec2      800     792      +8
fogStart               float      884     880      +4
fogEnd                 float      888     884      +4
near                   float      908     904      +4
far                    float      912     908      +4

total mismatched members: 42 / 60
```

The bundled `retina_lighting_reference` pack is itself affected — it reads `fogColor`,
`fogStart`, `fogEnd` and `sunAngle`. `fogStart` resolves to zero, `fogEnd` resolves to the
intended `fogStart`, and `sunAngle` resolves to a denormal, so `cos(sunAngle * 6.28)` is
effectively 1 and the day-cycle tint documented in `LIVE_RENDER_VALIDATION.md` never varies.

**Fix.** Give `vec3`/`ivec3`/`uvec3` size 12 with alignment 16. Then add the regression test
that would have caught it: compile the generated block and assert the class's offsets equal the
module's `OpMemberDecorate … Offset` decorations.

### B2 — Packs that declare their own vertex attributes never compile

`retina-core/…/translate/VulkanTranslator.java:208`

`collectDeclarations` recognises `varying`, `in`, `out` and `uniform`, but not `attribute`; and
`collectVaryings` deliberately excludes vertex-stage `in`, since there those are attributes
rather than varyings. Neither path assigns a location, so `attribute vec4 mc_Entity;` becomes
`in vec4 mc_Entity;` with no `layout(location=)`, which Vulkan GLSL rejects.

```
vsh:81: error: 'location' : SPIR-V requires location for user input/output
vsh:82: error: 'location' : SPIR-V requires location for user input/output
vsh:83: error: 'location' : SPIR-V requires location for user input/output
```

`mc_Entity`, `mc_midTexCoord`, `at_tangent` and `at_midBlock` appear in essentially every
published pack. This finding alone means no mainstream pack can load.

**Fix.** Collect vertex-stage `attribute` and `in` declarations into a second deterministic
layout assigned above the eight reserved legacy slots in `LegacyBuiltins`, and have the Sodium
and entity adapters feed the four well-known names. Refuse unknown attributes by name rather
than leaving them unqualified.

### B3 — A modern pack with an alpha test references an output that was never declared

`VulkanTranslator.java:852` (`injectAlphaTest`) against `buildPrologue:981`

When a pack declares its own fragment output — `out vec4 fragColor;`, normal in any GLSL 330+
pack — `hasExplicitOutputs` correctly suppresses Retina's generated `retina_FragData0`. But
`injectAlphaTest` still appends `if (… retina_FragData0.a …) { discard; }`, referring to a
variable that no longer exists. Every cutout pass on a modern pack fails.

```
vsh:77: error: 'location' : SPIR-V requires location for user input/output
fsh:79: error: 'location' : SPIR-V requires location for user input/output
fsh:83: error: 'retina_FragData0' : undeclared identifier
fsh:83: error: 'a' : vector swizzle selection out of range
```

**Fix.** When outputs are pack-declared, bind the alpha test to the declarator at location 0
rather than to the generated name — the translator already parses the declaration.

### B7 — `gradlew` is committed non-executable, so the documented build and CI both fail

`gradlew` — git mode `100644`

`./gradlew build`, the command printed in `README.md` and `docs/BUILDING.md`, returns
`Permission denied` on Linux and macOS. The single GitHub Actions run on record — id
`31773944589`, commit `2d108ae` — failed at *Build and verify release JAR* after **zero
seconds**, which is that failure rather than a Gradle error. No artifact was produced.

```
3  Set up Java 25               -> success
4  Set up Gradle                -> success
5  Build and verify release JAR -> failure   05:44:24 → 05:44:24  (0s)
6  Upload Retina JAR            -> skipped
```

This makes the README's claim that Actions "validates every pull request and every push to
`main`, then keeps the built Fabric mod JAR as a downloadable workflow artifact for 30 days"
untrue as written.

**Fix.** `git update-index --chmod=+x gradlew`. Add `chmod +x gradlew` as a defensive CI step,
and add a `-Pretina.coreOnly=true` job so the backend-neutral module keeps being tested even
when the Fabric repositories are unreachable.

### L1 — Minecraft source and assets are committed to a public LGPL repository

`net/minecraft/**` · `com/mojang/blaze3d/**` · `assets/minecraft/shaders/**` — ~260 KB, added
in `97cfcfa`

Fourteen tracked files contain decompiled Minecraft 26.2 and Blaze3D source (`LevelRenderer`,
`RenderPipelines`, `BindGroupLayouts`, `EntityRenderDispatcher`, `RenderPass`, `CommandEncoder`,
`RenderPipeline`, `RenderTarget`, `DefaultVertexFormat`) plus Minecraft's own
`entity.vsh`/`entity.fsh` and GLSL includes. They sit at the repository root, outside every
Gradle source set, so they are reference copies rather than build inputs.

Mojang's terms do not permit redistributing game code or assets, and `NOTICE` currently states
that Retina "does not bundle or redistribute Minecraft, Fabric API, Sodium, Iris, or their
source code" — which the repository contradicts. The project took care not to vendor Sodium
under its Polyform licence; this is the same problem with a larger rightsholder, and a hard
blocker for a Modrinth or CurseForge listing.

**Fix.** Remove all three trees from the working tree and from history before any release. If
the API surface needs to stay documented, keep a hand-written signature reference in `docs/` —
method names and shapes are facts, the decompiled bodies are not.

## High

### B4 — Extra `gl_FragData` writes are reported as "dropped" but break the compile

`VulkanTranslator.java:828`

Writing `gl_FragData[2]` under `DRAWBUFFERS:01` emits "the extra writes have no attachment and
were dropped". Nothing is dropped — the prologue declares outputs 0 and 1, so
`retina_FragData2` is undeclared and the pack fails with a message contradicting the warning the
user just read.

```
[warn] the program writes fragment output 2 but its DRAWBUFFERS directive
       declares only 2 target(s); the extra writes have no attachment and
       were dropped
fsh:83: error: 'retina_FragData2' : undeclared identifier
```

**Fix.** Pick one and make it true: declare the surplus outputs and let them go nowhere, or
raise a `CompilationException` naming the directive and the index.

### B5 — Array uniforms are silently downgraded to a single element

`VulkanTranslator.declaredNames:547`

`declaredNames` walks the declarators between the type and the semicolon, skips anything inside
brackets, and returns only the bare name. The dimension never reaches `blockUniforms`, so
`uniform vec3 lights[4];` is emitted into the generated block as a plain `vec3 lights;`.
`uniform vec3[4] lights;` behaves identically. Depending on how the pack indexes it the result
is a confusing type error or silently wrong code, since `lights[0]` on a `vec3` is a component
access that compiles.

```
===== uniform vec3 lights[4]; =====
  prologue emits : 'vec3 lights;'
===== uniform vec3[4] lights; =====
  prologue emits : 'vec3 lights;'

vsh:83: error: 'assign' : cannot convert from 'layout(std140 offset=64) temp highp float'
        to 'layout(location=0) smooth out highp 3-component vector of float'
```

The Fabric-side `TerrainShaderAdapter.MEMBER` regex requires `type name;` and cannot match an
array member — but it never sees one today, because the dimension is already gone by the time
the prologue is written, and `vec3 lights;` matches fine. That limitation goes live the moment
the first defect is fixed, so it belongs in the same change rather than being a second defect
now.

**Fix.** Carry the array length through `declaredNames` into the block member, widen `MEMBER` to
accept a bracketed suffix, and extend `TerrainUniformLayout.typeLayout` with the std140 array
rule (each element padded up to 16 bytes). `parseVaryingDeclaration` already parses array
lengths and can be reused.

### B6 — Multi-declarator varyings collide on a single location

`VulkanTranslator.qualifyVarying:233`

`varying vec2 a, b;` has its keyword token rewritten to `layout(location = 0) out`, which
applies to both declarators; `collectVaryings` only registers the first name, so `b` never gets
a slot.

```
vsh:80: error: 'location' : overlapping use of location 0
fsh:78: error: 'location' : overlapping use of location 0
```

**Fix.** Split multi-declarator varyings into one qualified declaration per name during
rewriting, and record every declarator in `collectVaryings`.

### C1 — Documentation asserts verification the code does not currently deliver

`README.md` · `docs/LIVE_RENDER_VALIDATION.md` · `docs/BENCHMARKS.md`

The docs are unusually honest about what is unimplemented, which makes the remaining
overstatements stand out. Three are load-bearing: the "playable lighting reference … applies
distance fog and day-cycle tint" claim is defeated by B1; the continuous-build claim is defeated
by B7; and the debug overlay and parallel-compilation settings the README advertises are inert
(B12). Minor drift: test counts appear as 73, 74 and 76 across documents — the true figures are
74 core plus 3 Fabric, which is what the README says and what this audit measured.

**Fix.** Fix B1, B7 and B12 rather than editing the prose. Then add a line to
`LIVE_RENDER_VALIDATION.md` distinguishing "activated without diagnostics" from "visually
confirmed in world" — a distinction items 15–19 already make and the summary loses.

## Performance

No profiling was possible here, so these are structural rather than measured. O1 and O2 sit
inside the per-draw loop.

- **O1 — Six mixin injections on the hottest path in the renderer.** `RenderPassMixin` injects
  at HEAD of `setPipeline`, `setUniform`, `bindTexture`, `setVertexBuffer`, `setIndexBuffer` and
  `drawIndexed`, so every draw call in the game pays six callbacks plus an `IdentityHashMap`
  probe, whether or not a pack is loaded. Gate the group behind one `static volatile boolean`
  set only when an active pack has an entity-shadow pipeline; the JIT can then fold the bodies
  away in the common case.
- **O2 — String comparisons on every pipeline bind.** `scenePipelineFor` runs from a
  `@ModifyArg` on every `setPipeline` and calls `getLocation().getPath()` followed by a chain of
  `equals`/`startsWith`. Vanilla `RenderPipeline` objects are singletons — resolve the mapping
  once at activation into an `IdentityHashMap<RenderPipeline, RenderPipeline>`.
- **O3 — Allocation churn per entity draw.** `captureEntityDraw` allocates a fresh
  `EntityDrawState` and copies two `HashMap`s for every entity draw in every frame. Copy only
  when the maps changed, or flatten the snapshot.
- **O4 — Around 800 full file reads per pack compile.** The prepare/shadowcomp/deferred/composite
  probe loops each run 100 iterations over two files and test existence with
  `source.readText(path).isPresent()`, which decompresses the whole ZIP entry.
  `PackSource.exists(PackPath)` already exists and is a hash probe. Use it, and stop at the first
  gap rather than always walking to 99.
- **O5 — Every shader file is read twice.** After the existence probe,
  `preprocessor.process(path, …)` reads the same entry again.
- **O6 — Whole-document regex passes over translated source.** `TerrainShaderAdapter.adapt` runs
  `replaceAll("set\\s*=\\s*\\d+\\s*,\\s*", "")` across the entire translated text — including
  pack code and comments — recompiling the pattern each call, to strip decorations the translator
  just emitted. Add a translator option that omits them instead.
- **O7 — The shader cache is designed but never used.** `dev.retina.core.cache.CacheKey` is
  written and tested and `RetinaClient` computes a cache directory, but nothing writes or reads a
  SPIR-V cache, so every activation re-runs shaderc for every stage.

## Interface

34 of the 56 keys in `en_us.json` are unreferenced, and they read as a map of a UI that was
specified and not built: `retina.error.title/.copy/.openLog/.keptPrevious/.fellBack`,
`retina.cost.vram/.passes/.shaders/.targets/.compileTime`,
`retina.screen.renderer.clearCache/.debugBundle`. Most of the below is finishing what those
strings promise.

- **U1 — Failures are a single line of grey text.** Shader diagnostics are the most important
  output a shader loader produces, and they currently cannot be read or copied. Build the error
  panel the strings already name: title, scrollable diagnostics with pack file and line (the
  preprocessor's provenance machinery exists for exactly this), Copy, Open log, and a line
  stating the previous pack is still running. Highest-value interface work in the project.
- **U2 — Nothing distinguishes selected from active.** Add an active badge; let Apply name the
  real transition.
- **U3 — Compilation is invisible.** Stage counts are known at compile time, so a real progress
  row is cheap. `retina.cost.*` suggests a cost summary was planned: targets, VRAM, compile time.
- **U4 — A pack is just a name in a list.** No author, version, description or preview. Reading
  `shaders.properties` and any bundled screenshot at discovery would cost little.
- **U5 — Resizing the window loses screen state.** `init()` recreates the search box empty and
  never restores the list's visual selection, though `selected` survives.
- **U6 — No keyboard path through the screen.** Enter to apply, arrows to move selection, Ctrl+F
  to focus search.
- **U7 — The renderer page has three controls and two are inert** (B12). Wire them up or remove
  them. If the overlay is built, its pass timings are the natural home for the protocol in
  `docs/BENCHMARKS.md`.

## Roadmap, by value over risk

| ID | Feature | Why it ranks here |
| --- | --- | --- |
| F1 | **`depthtex0` in composite and final** | `postSamplers` admits only colortex and shadow samplers. Depth is the most used input in any post chain — no SSAO, volumetrics, DOF, screen-space fog or water without it. The texture is already available; the underwater pass samples it today. |
| F2 | **A SPIR-V cache on disk** | Closes O7. Activation latency is the cost users feel most, and `CacheKey` is already written and tested. |
| F3 | **Custom vertex attributes** | Required to fix B2 regardless, and the gate for block-ID-driven effects: waving foliage, emissives, parallax, normal mapping. |
| F4 | **Wire up `block`/`item`/`entity.properties`** | `IdMap` is implemented and tested, but nothing feeds `entityId`, `blockEntityId` or `heldItemId` at runtime. The push-constant slots are already reserved in `UniformSchema`. |
| F5 | **A structured "why this pack failed" report** | Given the size of the compatibility gap, a diff of what the pack asked for against what Retina supports — written to a file a user can attach to an issue — may do more for adoption than any one feature, and turns every failed load into a prioritised backlog item. |
| F6 | **The `shaders.properties` screen and profile system** | `OptionScanner`/`OptionSet` already model pack options; missing are `screen.*`, `profile.*` and `sliders` — the layout directives that make a pack's own settings usable. |
| F7 | **`setup` passes, compute and SSBO** | Already on the roadmap. The gate for modern packs, and what `IS_IRIS=1` is currently writing cheques for (C2). |
| F8 | **Native `shadowcolor` attachments** | Removes the colortex round-trip the shadowcomp chain depends on; prerequisite for coloured shadows. |

## Suggested order

1. **B7** — one command, and it unblocks both CI and the build the docs tell people to run.
2. **B1** — a one-line change plus the offset regression test. Until it lands, every pack that
   reads a scalar uniform renders wrong and nothing downstream can be trusted.
3. **B2, B3, B5, B6** — the translator group. Together they are the reason no third-party pack
   loads, and they share a shape: declarations the location assigner does not see.
4. **L1** — remove the vendored Minecraft trees from the working tree and from history before
   anything is published anywhere.
5. **B12 and C1** — implement the advertised settings or withdraw them, and re-verify the
   reference pack's fog and tint once B1 is in.
6. **O1 and O2** — the two hot-path items, cheap to do and worth measuring once the debug overlay
   from U7 exists to measure with.
7. **U1** — the diagnostics panel. It makes every remaining compatibility gap self-reporting
   instead of a black screen.

---

One closing note in the project's favour. The separation between `retina-core` and
`retina-fabric` is real and load-bearing: it is what let this entire audit compile pack GLSL,
inspect SPIR-V, and reproduce six defects with no GPU, no Minecraft, and no window. Very few
renderer projects can be audited that way, and the defects above are shallow precisely because
the structure around them is not.
